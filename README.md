# Портал заявок — закупівлі та перевезення (тестове середовище)

Сервіс-деск портал (у стилі Jira Service Management) з двома сервісами:

* **Запит на закупівлю** — замовники замовляють товари по локаціях; закупівельники перевіряють нові позиції, беруть заявки в роботу, ведуть статуси позицій і формують зведену потребу з експортом в Excel/PDF.
* **Замовлення транспорту** (доставка та логістика) — замовники замовляють перевезення; диспетчери беруть заявки в роботу, призначають авто й закривають перевезення.

Спільне для обох: сповіщення замовнику (лічильник у «Мої заявки» + email), фільтри в усіх списках, історія змін у картці заявки.

## Швидкий старт (Windows)

Подвійний клік по **`start.cmd`** або в терміналі з папки проєкту:

```bash
start.cmd
```

Скрипт сам:
1. використовує портативний Node.js із `tools\node` (системний Node не потрібен);
2. встановить залежності, якщо немає `node_modules`;
3. сформує довідники `data\products.xlsx` і `data\locations.xlsx` (якщо їх ще немає);
4. створить БД `data\portal.db` із seed-даними — якщо її ще немає **або якщо після оновлення порталу змінилась структура БД**;
5. збере фронтенд (якщо змінювався код);
6. запустить **Mailpit** (перехоплення листів) і сервер.

| Що | Адреса |
|---|---|
| Портал | http://localhost:3000 |
| Mailpit (тестова пошта) | http://localhost:8025 |

Зупинка: `Ctrl+C` у вікні терміналу. Перестворити БД із чистими seed-даними:

```bash
start.cmd --reset
```

## Розгортання на Render

Web Service на Node, підключений до цього репозиторію (або Blueprint із `render.yaml`):

| Параметр | Значення |
|---|---|
| Runtime | Node (версія з `.node-version` — 22) |
| Build Command | `npm ci --include=dev && npm run build` |
| Start Command | `npm run start:prod` |
| Health Check Path | `/api/health` |
| Environment | `TZ=Europe/Kyiv`, `MAIL_MODE=outbox`, `COOKIE_SECRET=<випадковий рядок>` |

* Сервер слухає `0.0.0.0:$PORT` (Render задає `PORT` і `RENDER` сам), посилання в листах будуються з `RENDER_EXTERNAL_URL`.
* При першому старті (і після зміни структури БД) автоматично створюються seed-дані. `RESET_DB=true` — перестворити дані при кожному старті.
* **Листи** на Render не надсилаються: їх видно на сторінці **«Тестова пошта»** (кнопка вгорі праворуч, `/mail`). Щоб надсилати по-справжньому, задайте `MAIL_MODE=smtp` і `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_SECURE`, `MAIL_FROM`.
* **Дані на безкоштовному плані не постійні:** SQLite-файл живе на тимчасовому диску, тому після кожного деплою, перезапуску або «засинання» сервісу (≈15 хв без запитів) портал стартує з чистими seed-даними. Для постійних даних — платний план із Persistent Disk (змонтувати, напр., у `/var/data` і задати `DB_PATH=/var/data/portal.db`).
* Перший запит після «засинання» на безкоштовному плані відкривається ≈30–60 с.

## Seed-дані

* **Номенклатура** — 60 товарів із `data\products.xlsx` (категорія «Господарство») + 1 товар, доданий із заявки №3.
* **Локації** — 35. У репозиторії лише знеособлений зразок `data\locations.sample.xlsx` («Локація 01…35»). Реальний довідник покладіть у `data\locations.xlsx` (колонки «№», «Назва») і запустіть `start.cmd --reset` — він має пріоритет над зразком і в git не потрапляє.

## Сценарій 1. Закупівля з новими позиціями

1. **Замовник створює.** `customer1@test.ua` → «Каталог сервісів» → «Запит на закупівлю». У полі «Товар» введіть назву, якої немає в довіднику, наприклад `Килимок гумовий для входу` → «Додати новий товар: …». З'явиться вікно «Нова позиція» з підказкою схожих назв (спробуйте також `Губка для посуду` — запропонує наявні «Губки…»). Оберіть одиницю → «Додати нову позицію». Позиція позначена «нова позиція» і в довідник **не** потрапляє. Додайте ще одну нову позицію і звичайний товар, заповніть кількості, «Перевірити замовлення» → «Підтвердити».
   *Перевірка:* увійдіть як `customer2@test.ua`, почніть нову заявку і введіть `килимок` — у підказках його немає.
2. **Закупівельник бачить червоним.** `buyer1@test.ua` → «Вхідні заявки»: заявка має бейдж «⚑ Є нові позиції». У картці — блок «Нові позиції — немає в довіднику», рядки підсвічені червоним із підписом «Немає в довіднику».
3. **Виправлення (необов'язково).** «Виправити» → змініть назву/одиницю. Якщо ввести назву наявного товару (без урахування регістру, пробілів, латиниці/кирилиці) — позицію буде прив'язано до нього, дубль не створюється.
4. **Видалення з коментарем.** «Видалити з заявки» на одній з нових позицій → коментар обов'язковий → «Видалити з заявки». У Mailpit — лист замовнику з назвою товару й коментарем; у замовника — червоний лічильник у «Мої заявки» і рядок заявки виділено.
5. **Взяти в роботу.** «Взяти в роботу» → нові позиції, що залишились, додаються до довідника (категорія заявки, ознака «додано з заявки №ID»). Заявку, з якої видалено всі позиції, взяти в роботу не можна.
6. **Перевірка довідника.** `customer2@test.ua` → нова заявка → введіть `килимок`: товар є в підказках і більше не підсвічується як новий.

Готовий приклад: заявка **№6** (customer2) має 3 нові позиції.

## Сценарій 2. Перевезення

1. **Замовник створює.** `customer1@test.ua` → «Каталог сервісів» → «Замовлення транспорту» → «Замовити транспорт». Контакти підставляються з профілю. Заповніть завантаження, вантаж, вивантаження. Перевірте: без вибору «Потреба в печатці» (за замовчуванням «—») заявку не відправити; дата завантаження не в минулому; вивантаження не раніше завантаження. «Відправити заявку».
2. **Диспетчер повертає.** `dispatcher1@test.ua` → «Вхідні перевезення» (лічильник нових; нові — зверху й підсвічені). Відкрийте заявку → «Відправити на доопрацювання» → коментар обов'язковий. У Mailpit — лист; у замовника — сповіщення.
3. **Замовник виправляє.** `customer1@test.ua` → «Мої заявки» → «Перевезення» (рядок виділено) → заявка → «Редагувати» → «Зберегти та відправити». Статус знову «Нова».
4. **Диспетчер бере в роботу.** «Взяти в роботу» (атомарно: якщо інший диспетчер уже взяв — буде повідомлення).
5. **Дані авто.** «Внести дані по авто»: водій, телефон, номер авто (обов'язково), марка, посвідчення, дати (дата завантаження підставляється з заявки) → «Підтвердити». Статус «Авто призначено», замовнику — сповіщення і лист. Дані можна змінити пізніше («Змінити дані авто») — замовник знову отримає сповіщення.
6. **Замовник бачить авто.** У списку — номер авто та ПІБ водія, у картці — блок «Дані авто». Натисніть «Авто завантажено» → статус «Завантажено». (У диспетчера є дублююча кнопка.)
7. **Виконано.** Диспетчер → «Заявку виконано» (доступно лише в статусі «Завантажено») → статус «Виконано», зафіксовано дату виконання, замовнику — лист.

Уся історія (хто, коли, перехід статусу, коментар) видна в картці заявки обом сторонам.

## Сповіщення та email

* Лічильник на «Мої заявки» = непрочитані оновлення замовника (зміна статусу, дані авто, повернення на доопрацювання, видалення позиції). Оновлені заявки виділено в списках; після відкриття заявки оновлення вважається прочитаним.
* Email (через Mailpit): повернення на доопрацювання, видалення позиції, призначення/зміна авто, виконання.

## Фільтри (зберігаються під час переходу між сторінками)

* Замовник, закупівлі / закупівельник: №, статус, місяць поставки, наявність нових позицій (у «Вхідних» за замовчуванням — статус «Нова»).
* Замовник, перевезення: № або адреса, статус, період створення, період завантаження.
* Диспетчер: пошук за №, ПІБ замовника, адресою, номером авто, ПІБ водія; статус; період завантаження; «усі / мої»; потреба в печатці.

## Технічні деталі

* **Стек:** Node.js 22 (вбудований SQLite `node:sqlite`, TypeScript напряму), Express 5, React 18 + React Router, Vite, ExcelJS, pdfmake, Nodemailer → Mailpit.
* **Структура:** `server/services.ts` — закупівлі, нові позиції, сповіщення; `server/transport.ts` — перевезення; `server/mail.ts` — листи; `server/db.ts` — схема (версія 2); `src/pages` — сторінки; `src/components/Filters.tsx` — фільтри; `shared/` — статуси, нормалізація назв.
* **Модель закупівлі:** заявка → рядки (`request_lines`: товар довідника або нова позиція з назвою/од.) → позиції по локаціях (`request_items`).
* **Атомарність:** «Взяти в роботу» в обох сервісах — умовний `UPDATE … WHERE status = 'NEW'` у транзакції.
* **Режим розробки:** `npm run server` + `npm run dev` → http://localhost:5173.

## Обмеження MVP

* Вхід без пароля — лише для тестового середовища.
* Сповіщення в кабінеті оновлюються кожні 10 секунд (без push).
* Mailpit зберігає листи в пам'яті: після перезапуску вони зникають.
